# 実装前に必ず満たす7ガード
1. 「決済URLは、予約台帳にsession_idをattachした後にのみ会員へ返す」ことを保証し、テストで固定する。
   attach失敗時はURLを返さず、その予約をreconcileが拾える印を付ける（5分猶予の宙ぶらりん解放が安全に成立する前提）。
2. デプロイ移行中の互換のため、Netlifyは pending_expires_at_epoch が無い場合でも安全側
   （保持期限を延長しない／なければ再利用優先）にフォールバックする。

   取消→同枠取り直しが1タップで滑らかに完了する導線にすること。

   返金は行わない。

   別tokenで認証し、トークン無しは拒否。
7. 3件上限・サマリーの集計が新しいactive判定でズレないこと（expired/payment_failed/cancelledは数えない、
   一時的な長め保持が3件上限に少し影響するのは許容）。

# 本番反映の許可（このNagamachi BASE安定化作業に限る）
- Codexはオーナーのマシン上で本番反映まで実行してよい（clasp push / clasp deploy / Netlify本番反映）。
  レビュー/承認役はオーナー本人ではなく担当者が行う。
- 厳守事項:
  1. 反映は段階ごと。A反映後は「確認チェックリスト」を通し、担当者が緑を確認して「Bへ」とGOを出してからBに進む。
     待機日数は設けない（チェックが緑なら同日にBへ進んでよい）。ただしA反映から自動でBへ突き進まない。
     時刻系・サマリー・見回りなど時間依存の項目は、既存の「今すぐ実行」や手動トリガで即時に検証してよい。
     セッション自然期限切れ→枠解放だけは、テスト＋本番で1回の実地確認（約35分）で足りる。
  2. Stripeはテスト決済モード(sk_test_)のまま維持。live切替・Stripeダッシュボードのlive操作・
     LINE/KEYVOXの設定変更は自動で行わない（別途、明示指示が要る）。
  3. 反映の作法: テスト緑(npm test / node --check) → Apps Script先 → Netlify → 反映後にスモークチェック
     （新規予約/決済中断/再開/取消/決済成功でQR表示/LINE会員通知・運営通知・時刻一致）。
  4. 異常時は即ロールバック（Netlifyを直前deployへ、必要ならApps Scriptを前versionへ）。手順と結果を報告する。
  5. A段階は、コード＋テスト緑＋手順書まで作ったら“反映前に一旦提出して停止”し、担当者のレビュー後に反映する。
     B段階は、Aの本番確認後に担当者がGOを出してから着手・反映する。
